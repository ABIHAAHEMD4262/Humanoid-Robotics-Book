Mini-Project: Realistic Apartment Environment

Estimated Time: 90 minutes Prerequisites: Gazebo Setup, URDF/SDF Difficulty: Intermediate

Introduction​

You've learned the pieces. Now put them together. Build a complete simulation. A humanoid robot. A realistic apartment.

This project combines everything. Environment modeling. Sensor integration. ROS 2 communication. By the end, you have a working digital twin.

What You'll Build​

Your project includes:

  • A realistic apartment with multiple rooms
  • Furniture and obstacles
  • A humanoid robot with sensors
  • Real-time sensor data streaming
  • ROS 2 visualization

This is a real robotics project. You could expand it for research or development.

Example 1: Why Build a Digital Twin?​

Type: Scenario

Context: You want to test a home service robot. Buying a robot costs $15,000. Breaking things costs more.

Explanation: Build a digital twin first. Test in simulation. Find bugs. Fix problems. No risk. No cost. When it works, deploy to real hardware. Companies like Boston Dynamics do this. They test millions of scenarios. First in simulation. Then on real robots. This saves time. It saves money. It prevents accidents.

Takeaway: Digital twins let you fail fast and cheap. Perfect your system before touching real hardware.

Step 1: Create the Apartment World​

Start with a basic apartment layout.

worlds/apartment.sdf
<!-- Library: Gazebo Harmonic (osrf/gazebo latest)
     Last updated: 2025-12-05
     Tested on: Gazebo Harmonic, Ubuntu 22.04 -->

<?xml version="1.0"?>
<sdf version="1.9">
  <world name="apartment">

    <!-- Physics settings -->
    <physics name="physics" type="ode">
      <max_step_size>0.001</max_step_size>
      <real_time_factor>1.0</real_time_factor>
    </physics>

    <!-- Lighting -->
    <light name="sun" type="directional">
      <pose>0 0 10 0 0 0</pose>
      <diffuse>0.8 0.8 0.8 1</diffuse>
      <specular>0.2 0.2 0.2 1</specular>
      <direction>-0.5 0.1 -0.9</direction>
    </light>

    <!-- Ground plane -->
    <model name="ground_plane">
      <static>true</static>
      <link name="link">
        <collision name="collision">
          <geometry>
            <plane>
              <normal>0 0 1</normal>
            </plane>
          </geometry>
        </collision>
        <visual name="visual">
          <geometry>
            <plane>
              <normal>0 0 1</normal>
              <size>100 100</size>
            </plane>
          </geometry>
          <material>
            <ambient>0.8 0.8 0.8 1</ambient>
            <diffuse>0.8 0.8 0.8 1</diffuse>
          </material>
        </visual>
      </link>
    </model>

    <!-- Living room wall -->
    <model name="wall_north">
      <static>true</static>
      <pose>0 5 1.5 0 0 0</pose>
      <link name="link">
        <collision name="collision">

Step 2: Add Your Robot​

Include your humanoid robot model:

<!-- Add robot to world -->
<include>
  <uri>model://my_humanoid</uri>
  <pose>0 0 1.0 0 0 0</pose>
  <name>robot</name>
</include>

The robot spawns in the center. One meter above ground.

Step 3: Configure Sensors​

Your robot needs sensors. Add them to the robot SDF.

Camera Sensor​

models/my_humanoid/model.sdf
<sensor name="camera" type="camera">
  <pose>0.1 0 1.6 0 0 0</pose>
  <camera>
    <horizontal_fov>1.047</horizontal_fov>
    <image>
      <width>640</width>
      <height>480</height>
    </image>
    <clip>
      <near>0.1</near>
      <far>100</far>
    </clip>
  </camera>
  <update_rate>30</update_rate>
  <topic>/camera/image_raw</topic>
</sensor>

This creates a camera. It publishes to ROS 2. 30 frames per second.

Depth Camera​

<sensor name="depth_camera" type="depth_camera">
  <pose>0.1 0 1.6 0 0 0</pose>
  <camera>
    <horizontal_fov>1.047</horizontal_fov>
    <image>
      <width>640</width>
      <height>480</height>
      <format>R_FLOAT32</format>
    </image>
    <clip>
      <near>0.1</near>
      <far>10</far>
    </clip>
  </camera>
  <update_rate>10</update_rate>
  <topic>/camera/depth/image_raw</topic>
</sensor>

This provides depth information. Essential for navigation.

The IMU tracks orientation. It includes realistic noise.

Step 4: Launch File​

Create a launch file. This starts everything:

launch/apartment_sim.launch.py
# Library: ros2 launch v3.3.7
# Last updated: 2025-12-05
# Tested on: ROS 2 Humble, Python 3.10

from launch import LaunchDescription
from launch.actions import ExecuteProcess, IncludeLaunchDescription
from launch_ros.actions import Node

def generate_launch_description():
    return LaunchDescription([
        # Start Gazebo with apartment world
        ExecuteProcess(
            cmd=['gz', 'sim', '-r', 'apartment.sdf'],
            output='screen'
        ),

        # Start robot state publisher
        Node(
            package='robot_state_publisher',
            executable='robot_state_publisher',
            name='robot_state_publisher',
            parameters=[{'robot_description': 'path/to/your/robot.urdf'}],
            output='screen'
        ),

        # Start RViz with config
        Node(
            package='rviz2',
            executable='rviz2',
            name='rviz2',
            arguments=['-d', 'config/rviz_config.rviz'],
            output='screen'
        ),
    ])

This launches Gazebo. It starts RViz. It publishes robot state.

Step 5: Running Your Project​

Start the Simulation​

ros2 launch apartment_project apartment_sim.launch.py

Wait for Gazebo to load. This takes 10-30 seconds.

Check Topics​

Verify sensors publish data:

ros2 topic list

You should see:

  • /camera/image_raw
  • /camera/depth/image_raw
  • /imu
  • /joint_states

Monitor Data​

Check camera images:

ros2 run rqt_image_view rqt_image_view

Select /camera/image_raw. You should see the robot's view.

Check IMU data:

ros2 topic echo /imu

You should see orientation and acceleration updates.

Example 2: Debugging Sensors​

Type: Scenario

Context: Your camera shows black. No image appears.

Explanation: First, check the topic. Run ros2 topic echo /camera/image_raw. If no data appears, the sensor isn't publishing. Check your SDF file. Is the camera plugin loaded? Does the topic name match? If data appears in echo but not in rqt_image_view, check the image format. RGB8 is standard. Still broken? Check Gazebo console for errors. Most problems are typos or missing plugins.

Takeaway: Debugging sensors requires systematic checks. Topics, plugins, formats, and error logs.

Step 6: Testing and Validation​

Performance Test​

Check simulation speed:

gz topic -e -t /stats

Look for real_time_factor. Should be close to 1.0. If below 0.5, your simulation is too slow.

Sensor Rate Test​

Measure camera frame rate:

ros2 topic hz /camera/image_raw

Should report around 30 Hz. If lower, something is wrong.

Navigation Test​

Move the robot. Use keyboard teleop:

ros2 run teleop_twist_keyboard teleop_twist_keyboard

The robot should move smoothly. No jitter. No crashes.

Common Issues​

Issue 1: Simulation is Slow​

Problem: Real-time factor below 0.5.

Solutions:

  • Reduce physics step size
  • Simplify models (fewer polygons)
  • Disable shadows in Gazebo
  • Use simpler sensor configurations

Issue 2: Robot Falls Through Floor​

Problem: Robot spawns and immediately falls.

Solution: Check collision geometries. Ensure ground plane has collision element. Verify robot spawn height is correct.

Issue 3: No Sensor Data​

Problem: Topics exist but no data.

Solutions:

  • Check plugin is loaded
  • Verify topic names match
  • Ensure sensors have update_rate set
  • Check Gazebo console for errors
